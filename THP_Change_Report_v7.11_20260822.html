Resume access New "📄 View Resume" button in the candidate detail modal (viewCandModal), opens r[C.resumeLink] in a new tab. This is the Portal-written resume URL — previously the Portal wrote resumes into DocumentLink, which this app's own createMeeting() silently overwrites with the interview venue/Teams link the moment an interview is scheduled. The Portal now writes resumes to the new, separate ResumeLink field instead (shipped to production 22 Aug 2026); this app's createMeeting() is untouched and keeps using docLink exactly as before. Verified
Confirmed live (Portal side) that resumes now land in ResumeLink, not DocumentLink. Button only renders when a candidate actually has a resume link.
Resume Fitment Vs JD New computeResumeFitment(code): downloads the candidate's resume PDF, extracts text client-side (pdf.js), compares it against the role's existing Repository JD entry (role context, core questions, shortlist/red-flag indicators — reused rather than re-extracting the JD PDF a second time), and calls Claude for a 1-10 score plus specific recruiter recommendations. Result stored in the new ResumeFitmentData column as JSON — not in igEvalData/the Evaluations sheet, a deliberate separation so it can never be touched by the manual-scores save path. Shown in the candidate detail modal, the Interview Guide's Evaluation page (new "AI-Assisted Signals" block), and as a 🔍 icon next to the candidate's name in the main list. Needs Anne's live test
PDF extraction verified working end-to-end (real test PDF generated and read back correctly in-browser). The Anthropic call itself uses the exact same fetch pattern as the already-live igAISummary() — same headers, same key mechanism — but wasn't independently re-tested against a live key, since doing so would need a real logged-in session this environment can't reach (MSAL redirect URI is configured for the live Pages URL, not localhost). Recommend: after deploy, run it once against a real Portal-sourced candidate with a resume on file.
AI video interview invite New "🎥 Invite to AI Interview" button (candidate detail modal). Writes an ISO timestamp to VideoInterviewInvited and saves via the existing xlPatchRow path, then opens a modal with the interview link and a pre-filled mailto: draft for the recruiter to review and send — this app has no server of its own to send email directly, same reasoning as the existing "Send WhatsApp Confirmation" button pattern elsewhere in this app. The Portal's /interview/[code] now refuses access until this flag is set — previously anyone who found that URL and could verify their own email could start an interview for any role; that gap is now closed on the Portal side (shipped 22 Aug 2026). Verified
Portal-side gate tested live: a non-invited email is correctly rejected with 403 before this button's flag exists to unblock it.
AI video interview results New viewVideoInterview(code) modal: video playback, the four AI-scored rubric areas (Communication, Role Knowledge, Example Quality, Ownership/Follow-up — the same rubric labels as the existing manual Evaluation Scores below), the AI summary, and a per-question transcript. Reachable from the candidate detail modal and the Interview Guide's Evaluation page. Read directly from VideoInterviewData (written by the Portal after a candidate completes an interview) — this app never writes to that field, only reads it. Verified
Portal-side pipeline (recording → transcription → AI scoring → this exact field) verified end-to-end against live infrastructure in the Talent Gateway repo before this UI was built against it.
Evaluation audit trail New "📜 Previous Rounds" button on the Evaluation page, backed by fetchEvaluationHistory(code). Turns out igSaveEval() already appends a new row to the Evaluations sheet on every save rather than overwriting — nothing was ever actually being destroyed at the storage layer. The real gap was that nothing ever surfaced earlier rows; igEvalData[code] only ever held whichever row loaded last. This reads every row for a candidate directly from the sheet and lists each round (timestamp, recruiter, recommendation, scores, summary) newest-first. No change to the save path itself — it was already correct. Depends on workbook access
Uses the same Graph pattern as the existing fetchLiveChangeLog().
