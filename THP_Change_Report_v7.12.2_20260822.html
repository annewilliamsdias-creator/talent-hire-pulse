v7.12.1 — Transcript mapping and persistence fixes  |  22 Aug 2026 v7.12.1

CR TitleWhat ChangedTest Status
Transcript mapped to wrong question (Portal-side root cause) Anne reported answers to 5+ questions showing up against only 3, with unrelated answers (e.g. system-usage questions) landing on Q1. Root cause found in the Portal's own transcription pipeline (talent-gateway/lib/interview-processing.ts, separate repo): the per-question time boundaries passed to the transcript segmenter were filtered to answered questions only, before segmentation ran. Any skipped question's start-time boundary vanished from the timeline as a result — the segment for the question just before a skip silently absorbed the skipped gap and bled into whatever the candidate said on the next answered question, compounding with every subsequent skip. Fixed to pass every logged question (skipped or not) as a boundary, and only filter to answered-only afterward, for scoring. Separate possible contributing factor: if Anne's test session was a continuation of the earlier CORS-failure tab (recorder already stopped, no further audio actually captured) rather than a fresh session, that alone would also produce exactly this symptom — worth confirming on retest whether a genuinely fresh tab still shows any misattribution. Verified
Portal-side change, verified via tsc and a clean production build (talent-gateway commit ad20d53). Not independently re-tested against a live transcription job — would need a real interview submission to confirm end-to-end.
AI-interview note "disappearing" after AI Summary v7.12 originally wrote the transcript into the question's note field the first time Page 3 rendered. That made what showed up depend on visit order: if AI Summary ran (which reads notes to build its prompt, then auto-saves) before Page 3 had ever rendered in that session, nothing had been written yet — nothing to save, and revisiting Page 3 afterward could look like the content had been removed. Reworked so the transcript is never written into igEvalData at all — igEffectiveNote() computes it fresh from r[C.videoInterviewData] every time it's needed (Page 3's display and AI Summary's prompt-building both call the same function now), and a recruiter's own saved edit (via typing into the field) always takes priority. Nothing session- or order-dependent left in this path. Verified
Confirmed with mock data: igEvalData[code].notes stays {} after rendering Page 3 (nothing written), the AI Summary prompt-builder still correctly pulls the transcript for answered questions and correctly leaves a skipped one blank, using the exact same fallback logic as the display.

v7.12.2 — Recruiter-side resume upload  |  22 Aug 2026 v7.12.2

CR TitleWhat ChangedTest Status
Resume upload (Edit Profile + candidate modal) Until now, ResumeLink only ever got populated by the Portal — a candidate sourced directly by a recruiter (not through Talent+ Gateway) had no way to get a resume on file for Resume Fitment scoring or the "View Resume" button. Added a file field to the Edit Profile form (📄 Resume section, PDF/DOC/DOCX, max 5MB) and a standalone "📤 Upload Resume" / "Replace Resume" button in the candidate detail modal next to "Invite to AI Interview", both calling the same new uploadResumeToSharePoint(). Files upload via a plain Graph PUT to a new Resumes/ subfolder in the same SharePoint document library THP already writes backups to — no new permissions, no new credentials, same delegated Sites.ReadWrite.All scope already granted. The resulting link is written to the same ResumeLink field the Portal uses, so every downstream feature (View Resume, Score Resume Fitment) works identically regardless of source. Verified
Confirmed both entry points render correctly and read/write the right candidate record (button label switches Upload↔Replace based on existing link; Edit Profile shows "View current resume" or "No resume on file yet" correctly on lookup). The actual Graph PUT itself wasn't re-tested against a live upload — same code pattern as the already-live autoBackup() function, not independently verified end-to-end.
